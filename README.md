# 주문·재고·발주 통합 웹

물류 담당자가 배송일별로 무엇을 준비할 수 있고 무엇이 막혀 있는지 보고, 막힌 주문은 발주로
풀어내는 도구입니다. 제품·주문·발주 세 화면이 같은 데이터를 다른 관점에서 보여 주고,
한쪽에서 처리하면 다른 쪽에 바로 반영됩니다.

업무 기준시각은 **2026-07-21 09:00** 입니다. 실제 시계를 쓰면 데이터의 배송예정일이 전부
과거가 되어 "배송일 전날까지 쓸 수 있는 입고예정" 같은 규칙이 의미를 잃습니다. 그래서
`app.base-time` 으로 고정 `Clock` 을 주입하고, 업무 판단에 쓰는 '오늘'은 모두 거기서 가져옵니다.

| | |

| 스택 | Java 17 · Spring Boot 4 · JPA · MySQL 8.4 / Next.js 16 · React 19 · TypeScript · SWR |

| 화면 | 제품 · 주문 · 발주 |

## 실행

Java 17, Node 20 이상, Docker 가 필요합니다. 터미널 3개를 씁니다.

```bash
# 1) MySQL — 스키마와 과제 데이터가 이때 한 번 적재됩니다
#    ※ 반드시 저장소 루트에서 실행해 주세요 (compose 가 상대경로로 SQL 을 마운트합니다)
docker compose up -d

# 2) 백엔드 — http://localhost:8080
cd back && ./gradlew bootRun

# 3) 화면 — http://localhost:3000
cd front && npm install && npm run dev
```

**브라우저에서 http://localhost:3000 을 열면 됩니다.** 제품 `/items`, 주문 `/orders`,
발주 `/schedules` 입니다.

브라우저는 같은 오리진의 `/api` 로만 호출하고 `front/next.config.ts` 의 rewrite 가
8080 으로 넘깁니다. CORS 설정을 서버에 두지 않으려고 이렇게 했습니다. 백엔드 주소를 바꾸려면
`front/.env` 에 `API_ORIGIN` 을 넣어 주세요 (`front/.env.example` 참고).

### 데이터 적재

엑셀 업로드 화면 대신 SQL 시드를 썼습니다. compose 가 아래 두 파일을 컨테이너의
`/docker-entrypoint-initdb.d` 로 마운트합니다.

| 파일 | 내용 |
| --- | --- |
| `back/src/main/resources/schema/schema.sql` | 13개 테이블 DDL |
| `back/src/main/resources/schema/sample.sql` | 과제 엑셀을 옮긴 기준 데이터 (10개 테이블) |

엑셀의 한글 업무값을 코드로 치환한 규칙과, 스키마에 자리가 없어 옮기지 못한 컬럼은
`sample.sql` 상단 주석에 적어 뒀습니다.

initdb 는 **데이터 디렉터리가 비어 있을 때만** 돕니다. 그래서 앱이 처리한 예약·출고·입고
결과는 컨테이너를 다시 띄워도 남습니다. 매번 적재하면 `sample.sql` 의 `DELETE` 가 그동안의
처리 결과를 지우기 때문에, 앱 쪽은 `ddl-auto: validate` + `sql.init.mode: never` 로 두고
아무것도 실행하지 않습니다.

기준 데이터로 되돌리려면 볼륨째 지웁니다.

```bash
docker compose down -v && docker compose up -d
```

### 테스트

```bash
cd back  && ./gradlew test    # 74개. Docker 만 떠 있으면 됩니다
```

백엔드 테스트는 앱이나 개발용 DB 를 띄우지 않아도 됩니다. Testcontainers 로 자기 MySQL 을
띄우고 끝나면 버립니다.

## 5분 데모

처음 보실 때 이 순서로 따라가시면 과제가 요구한 연결(4-4)을 전부 확인하실 수 있습니다.
아래 주문번호는 전부 테스트가 단언하고 있는 값입니다.

**① 판정이 갈리는 걸 본다 — 주문 화면**

| 주문 | 상태 | 왜 |
| --- | --- | --- |
| `ORD202607200016` | 바로 준비 가능 | 세트 1건이 구성품 3개로 전개됨 (설치·수거 서비스는 빠짐) |
| `ORD202607200007` | 품질검사 대기 | `MO-20260721-Z10` 의 검사를 기다림 |
| `ORD202607200019` | 구매 입고 대기 | 현재고 2 + 입고예정 1 |
| `ORD202607200015` | 재고 부족 | `MAT-V3-Q` 1개 부족. `CVR-WP-Q` 는 남아 있지만 **일부만 잡지 않음** |
| `ORD202607200011` | 확인 필요 | 주문서의 `UNKNOWN-SKU` 가 품목에 없음 |

`ORD202607200009`(바로 준비 가능, 가용 8)와 `ORD202607200012`(재고 부족, 가용 4)를 나란히
보시면 **앞 주문이 가져간 재고가 뒤 주문에서 빠져 있는 것**이 보입니다. 같은 `PIL-ZERO` 입니다.

**② 예약 → 피킹 → 출고 — `ORD202607200001`**

`재고 예약` 을 누르면 현재고는 그대로고 예약수량만 늡니다. 이어서 출고할 제품을 직접 고르거나
`자동 배정` 을 누르고, `출고 처리` 를 하면 그때 현재고가 줄어듭니다. 제품 화면에서 같은 숫자가
움직이는 걸 확인하실 수 있습니다.

**③ 부족 → 발주 → 입고 → 재판정 — `ORD202607200024`**

부족 품목 `FRM-LOW-Q`(매입품)에서 발주를 만들면 구매발주가 생기고 발주 화면으로 넘어갑니다.
아직 현재고는 0 입니다. 입고 처리를 하면 현재고가 늘고, 그 문서를 기다리던 주문이
`재고 부족` 에서 풀립니다. 생산품은 `ORD202607200020` → `MAT-E5-SS` 로 보시면 되는데,
이쪽은 품질검사를 기록해야 입고가 열립니다.

## 화면

| 화면 | 내용 |
| --- | --- |
| **제품** `/items` | 창고별 현재고·예약수량·가용재고(사용 중지 창고는 따로 표시), 예약수량을 잡고 있는 주문, 시리얼 개체와 배정된 주문, 이 품목을 기다리는 주문, 걸려 있는 발주 문서, 수량 변동 이력 |
| **주문** `/orders` | 준비 판정과 부족수량, 원 주문 라인과 세트 전개 결과, 예약→피킹→출고 액션, 출고할 시리얼 제품 직접 선택·해제, 부족 품목에서 발주 생성(공급처·예정일 선택), 여러 주문 묶음 발주. 배송일·창고·준비상태 필터 |
| **발주** `/schedules` | 제공된 문서와 앱에서 만든 문서가 한 목록에, 확정·품질검사(부분 합격)·입고 처리, 어느 주문 때문에 생겼는지, 입고하면 풀릴 주문 |

세 화면은 품목코드·주문번호·문서번호를 주소에 실어 서로 오갑니다. 목록 위 요약 카드를 누르면
그 상태로 걸러지고, 막힌 주문(재고 부족·확인 필요)은 줄 색을 다르게 해서 먼저 눈에 띄게 했습니다.

화면은 **버튼만 두지 않고 결과를 먼저 보여 주려고 했습니다.** 발주 버튼 옆에는
`공급처 리드타임 → 사용 가능 예정일 → 배송 전날` 을 비교한 결과가 같이 나옵니다. 기한을 넘기면
버튼을 잠그고 사유를 띄우며, 리드타임이 짧은 다른 공급처를 그 자리에서 골라 다시 계산할 수
있습니다. 눌러 놓고 나중에 납기를 놓치는 상황을 화면에서 먼저 막고 싶었습니다.

## 구조

```
back/   Spring Boot — 판정·명령·정합성. 계산은 전부 여기 있습니다
front/  Next.js — 서버가 준 값을 그리기만 합니다
```

화면이 따로 계산하면 담당자가 보는 숫자와 실제로 반영되는 숫자가 갈라집니다. 그래서 준비
판정·세트 전개·부족수량은 화면에서 다시 계산하지 않습니다. 명령이 끝나면 SWR 로 열려 있는
키를 한 번에 무효화해서 세 화면이 같은 숫자를 봅니다.

읽어 보실 곳은 네 군데입니다.

| 클래스 | 하는 일 |
| --- | --- |
| `ReadinessPlanner` | 준비 판정. 우선순위대로 재고를 나눠 줍니다 |
| `SetExpander` | 주문 라인 → 실제 준비 품목 |
| `OrderCommandService` | 예약 · 피킹 · 출고 (재고가 주는 쪽) |
| `ScheduleCommandService` | 발주 · 검사 · 입고 (재고가 느는 쪽) |

## 준비 판정

전개는 `SetExpander`, 판정은 `ReadinessPlanner` 가 합니다. 둘 다 아무것도 저장하지 않고
조회할 때마다 계산합니다. 준비 상태를 컬럼으로 들고 있으면 재고가 바뀔 때마다 모든 주문을
갱신해야 하고, 갱신을 놓친 행이 그대로 거짓말이 됩니다.

### 세트 전개

- `주문 확정` 상태의 `정상` 라인만 대상입니다. 취소 라인은 기록만 남기고 수량에서 뺍니다.
- 세트는 구성품으로 **한 단계** 전개합니다. 세트 자체는 출고하지 않습니다.
- 출고 대상이 아닌 구성품(설치·수거)과 서비스 품목은 재고 수요를 만들지 않습니다.
  단품으로 주문된 서비스도 같습니다.
- 같은 품목이 일반 주문행과 세트 구성품에 함께 나오면 합산합니다.

### 전역 배분

여기가 제일 조심한 부분입니다. 주문을 하나씩 따로 보면 같은 재고를 여러 주문이 중복으로 세어
**전부 "준비 가능"으로 보입니다.** 숫자가 조용히 틀려서 화면만 봐서는 모릅니다.

그래서 배송예정일 → 주문접수일시 순으로 훑으면서, 앞선 주문이 가져간 수량을 재고 풀과
입고예정 풀에서 빼고 다음 주문을 판정합니다.

- 한 주문은 **필요한 모든 품목을 채울 수 있을 때만** 풀을 소비합니다. 한 품목이라도 부족하면
  아무것도 잡지 않고 풀을 그대로 둬서 뒤 주문이 씁니다.
- 현재고만으로 되면 `바로 준비 가능`, 입고예정을 써야 하면 기다리는 원인을 보여 줍니다
  (`품질검사 대기` / `생산 완료 대기` / `구매 입고 대기`).
- 입고예정까지 더해도 못 채우면 `재고 부족` 이고, 이 주문이 발주 대상입니다.

한 가지 빠뜨렸다가 고친 게 있습니다. 이미 예약이 잡힌 주문은 그 수량이 `booked_quantity` 에
이미 빠져 있는데, 처음에는 풀에서 한 번 더 뺐습니다. 그랬더니 예약을 마친 주문이 스스로
재고 부족으로 뒤집히고 뒤 주문들도 재고가 실제보다 적다고 판단했습니다. 지금은 예약된 주문을
따로 구분합니다.

### 입고예정을 쓸 수 있는지

판단은 `StockSchedule.isUsableForPlanning()` **한 곳에서만** 합니다. 미확정 문서, 사용 중지된
창고로 들어오는 문서, 남은 수량이 없는 문서, 사용 가능 예정일이 없는 문서, 검사 불합격 문서를
제외합니다. 여기에 더해 각 주문은 **배송일 전날까지** 쓸 수 있는 문서만 씁니다.
화면의 "판정 반영 / 제외" 배지도 같은 메서드를 쓰기 때문에 둘이 어긋날 수 없습니다.

주문은 지정된 출고창고의 재고만 씁니다. 다른 창고에 수량이 있어도 자동으로 합치지 않습니다.
대신 화면에는 "다른 창고 재고 N개 · 자동 사용되지 않으며 창고 이동은 별도 검토가 필요합니다"
라고 보여 줍니다.

### 확인이 필요한 주문

미등록 품목, 사용 중지된 창고, 잘못된 수량은 임의로 고치지 않습니다. **재고를 건드리지 않고
풀도 소비하지 않으며** 발주 대상에서도 뺍니다. 화면이 버튼을 감추는 것과 별개로 **API 에서도
막았습니다.** 수량을 직접 지정해 호출하면 부족수량 조회를 건너뛰기 때문에, 판정 상태를 보고
거절하지 않으면 규칙이 뚫립니다.

사유는 무엇을 고쳐야 하는지까지 적습니다.

> 1번 품목 `UNKNOWN-SKU` 가 품목으로 등록되어 있지 않습니다. 품목 등록 후 다시 확인해 주세요.

이러려면 원본 코드를 버리면 안 됩니다. 그래서 `order_detail` 은 품목 FK 가 없는 라인을
허용하고(`item_id` NULL) 원본을 `raw_item_code` 에 남깁니다. 라인을 아예 넣지 않으면
"주문 상세가 없습니다" 까지밖에 말할 수 없습니다.

취소·출고 완료·배송 완료 주문은 `확인 필요` 가 아니라 **`준비 대상 아님`** 으로 따로 뒀습니다.
`확인 필요` 는 사람이 손봐야 한다는 뜻이고 이쪽은 정상적으로 끝났다는 뜻이라, 같은 값으로 두면
담당자 처리 목록에 이미 끝난 주문이 섞입니다.

## 부족수량과 발주·입고

부족수량은 `필요수량 - (가용재고 + 그 주문이 쓸 수 있는 입고예정 잔여수량)` 입니다. 따로
계산하지 않고 **위 전역 배분이 그 주문 차례에 실제로 확보하지 못한 수량**을 그대로 씁니다.
앞선 주문들이 가져간 몫이 반영된 값이어야 의미가 있습니다.

- 매입품은 구매발주(`PO-`), 생산품은 생산의뢰(`MO-`)로 만듭니다. 서비스 품목과 세트 자체는
  발주 대상이 아니고, 세트는 구성품 단위로 발주합니다.
- 입고창고는 그 주문의 출고창고와 같습니다. 사용 중지된 창고로는 발주할 수 없습니다.
- 공급처 기본값은 품목의 기본 공급처, 사용 가능 예정일 기본값은 `기준시각 + 리드타임` 이고
  둘 다 화면에서 바꿀 수 있습니다.
- `stock_schedule.order_id` 로 어느 주문 때문에 생겼는지 남기고, 주문 상세에서도 이 주문이
  기다리는 문서를 볼 수 있습니다.

**발주를 만든 것만으로 현재고는 늘지 않습니다.** 입고 처리에서만 늘어납니다.

### 품질검사

생산의뢰는 검사를 통과해야 입고할 수 있습니다. 검사는 합격/불합격이 아니라 **통과 수량**을
받습니다. 생산 물량 중 일부만 합격하는 게 오히려 흔해서입니다. 계획수량이 2인데 1개만
합격했다면 남은 계획수량이 1 있어도 더 넣을 수 없습니다.

불합격분은 들어오지 않으므로 **준비 판정에서도 빠집니다.** 이걸 구분하지 않으면 들어오지 않을
물량을 기다리며 주문이 `생산 완료 대기` 로 남고, 담당자는 발주할 시점을 놓칩니다. 그 주문은
`재고 부족` 으로 바뀌어 발주 대상이 되는 게 맞습니다.

전량 불합격이어도 `검사 대기` 로 되돌리지 않고 `검사 불합격` 으로 남깁니다. 되돌리면 이미
검사 대기였던 문서에서는 불합격이 아무것도 바꾸지 않아서, 담당자가 기록이 남았는지 알 수
없습니다. (처음에 그렇게 만들었다가 고쳤습니다.)

이미 입고된 수량보다 낮게 통과 수량을 낮출 수는 없습니다. 입고를 취소하는 기능이 아닙니다.

### 수량 세 가지

같은 문서에서 수량이 세 갈래로 갈려서, 화면과 API 가 셋을 따로 내려 줍니다.

| 값 | 뜻 |
| --- | --- |
| `remainingQuantity` | 계획수량 − 입고수량. 문서상 아직 안 들어온 수량 |
| `receivableQuantity` | 지금 입고할 수 있는 수량. 생산의뢰는 검사 통과분까지 |
| `usableQuantity` | 준비 판정이 세는 수량. 불합격분이 빠진 값 |

누적 입고수량은 계획수량을 넘을 수 없고, 시리얼 관리 품목을 입고하면 수량만큼 개체가 생깁니다.
시리얼번호는 DB UNIQUE 로 막혀 있습니다.

### 묶음 발주 (선택 사항)

같은 품목을 여러 주문이 조금씩 부족해하는 경우가 많습니다. 주문마다 따로 발주하면 같은
공급처에 1~2개짜리 문서가 여러 건 나갑니다. 그래서 **같은 품목·같은 입고창고**의 부족분을
한 문서로 합치는 `POST /api/stock-schedules` 를 뒀습니다. 부족 화면에서 한 품목에 막힌 주문이
2건 이상이면 버튼이 나타납니다.

한 문서는 한 창고로만 들어오므로 출고창고가 다른 주문끼리는 묶지 않고, 어느 창고들인지
사유에 적어 거절합니다. 문서는 배송일이 가장 빠른 주문에 연결합니다. 나머지 주문도 같은 품목을
기다리고 있으니 입고되면 판정이 다시 돌아 함께 풀립니다.

## 중복 요청 처리

반복 요청을 두 성격으로 나눠서 다르게 막았습니다.

**상태로 구분되는 것은 상태로 막습니다.** 이미 예약이 있으면 다시 예약하지 않고 현재 상태를
돌려줍니다. 이미 출고된 주문은 아무것도 바꾸지 않습니다. 피킹은 이미 배정된 개체 수를 세어
모자란 만큼만 채우고, 직접 고른 개체를 다시 보내도 이미 이 주문 것이면 넘어갑니다.

**상태로 구분할 수 없는 것은 멱등 키를 씁니다.** 발주 생성과 입고 처리는 "같은 수량을 또
넣는 것"이 업무적으로 정상일 수 있어서, 상태만으로는 중복인지 판단할 수 없습니다.
`Idempotency-Key` 헤더로 키를 받아 `request_log` 에 저장하고, 같은 키가 다시 오면 처음 처리한
결과를 그대로 돌려줍니다.

키는 **요청 내용으로** 만듭니다. 호출할 때마다 난수를 뽑으면 네트워크 재시도만 막고 담당자가
버튼을 두 번 누르는 건 못 막는데, 실제로 중복이 생기는 자리는 후자입니다.

| 명령 | 키 | 두 번 눌렀을 때 |
| --- | --- | --- |
| 발주 생성 | `po:{주문번호}:{품목코드}:{수량}` | 문서가 하나만 생김 |
| 입고 처리 | `rcv:{문서번호}:{누적입고수량}:{수량}` | 현재고가 한 번만 늚 |

입고 키에 **그 시점의 누적 입고수량**을 넣은 건 같은 수량을 한 번 더 넣는 분할 입고가
정상이기 때문입니다. 첫 입고가 반영되면 누적수량이 달라져 다음 요청은 새 키가 되고,
반영되지 않았다면 같은 키라 서버가 막습니다. "실수로 두 번"과 "의도해서 두 번"이 구분됩니다.

중복을 실제로 막는 건 코드가 아니라 **DB 제약**입니다. 코드로만 검사하면 두 요청이 같은 순간에
검사를 통과할 수 있습니다.

| 제약 | 막는 것 |
| --- | --- |
| `request_log.idempotency_key` UNIQUE | 같은 키의 발주 생성·입고가 두 번 반영되는 것 |
| `order_reservation (order_id, item_id)` UNIQUE | 같은 주문·품목이 두 번 예약되는 것 |
| `item_unit.serial_number` UNIQUE | 시리얼번호가 중복 생성되는 것 |

데이터 적재 쪽 중복은 `sample.sql` 이 전체 `DELETE` 후 명시적 id 로 `INSERT` 하도록 짜서,
몇 번 다시 돌려도 같은 결과가 됩니다.

## 숫자 정합성

모든 수량 변경은 한 트랜잭션 안에서 일어나고, 바꿀 행을 먼저 `SELECT ... FOR UPDATE` 로
잠급니다. 격리수준은 `REPEATABLE READ` 입니다.

| 단계 | 방식 |
| --- | --- |
| 예약 | 재고 행을 잠그면서 DB 최신 값으로 덮어쓴다. 한 품목이라도 모자라면 예외를 던져 앞서 잡은 예약까지 전부 되돌린다 |
| 피킹 | 예약 행과 개체 행을 잠근다. 보관 중인 개체만 고르므로 같은 개체가 두 주문에 들어가지 않는다. 한 개라도 조건에 맞지 않으면 한 개도 배정하지 않는다 |
| 출고 | 현재고와 그 주문의 예약수량을 함께 줄인다. 예약을 `출고 완료` 로 표시해 반복 호출해도 한 번만 반영된다. 시리얼 피킹이 끝나지 않으면 거부한다 |
| 입고 | 문서 행을 잠그고 누적 입고수량이 계획수량을 넘는지 검사한다 |

### 락만으로는 부족했던 자리

예약은 바로 앞에서 준비 판정을 돌리는데, 판정이 같은 트랜잭션에서 전 재고를 읽어
영속성 컨텍스트에 올려 둡니다. 이 상태로 재고 행을 `FOR UPDATE` 로 다시 조회하면 하이버네이트가
읽어온 값을 버리고 **캐시에 있던 인스턴스를 돌려줍니다. 락은 잡히는데 숫자는 판정 시점 그대로입니다.**

처음에 이걸 모르고 조회만 다시 했다가, 동시 예약 테스트에서 뒤 트랜잭션이 옛날 값 위에 덮어써
앞 트랜잭션의 예약이 통째로 사라지는 걸 보고 알았습니다. 지금은 `EntityManager.refresh(stock,
PESSIMISTIC_WRITE)` 로 행을 잠그면서 엔티티 상태까지 DB 값으로 덮어씁니다.

### 락 순서

재고 행은 **품목코드 순으로** 잠급니다. 주문 라인 순서대로 잠그면 A 주문이 X→Y, B 주문이
Y→X 를 동시에 잡을 때 서로를 기다리다 데드락이 납니다. 모든 요청이 같은 순서로 잠그면 뒤에 온
요청은 첫 행에서 막혀 기다릴 뿐입니다. 피킹도 같은 이유로 시리얼번호 순으로 잠급니다.

그래도 락 대기 초과나 데드락이 나면 `ApiExceptionHandler` 가 409 와 한글 사유로 바꿔 줍니다.
그 요청은 통째로 롤백되었으니 숫자는 어긋나지 않았고, 다시 시도하면 되는 상황입니다.

### 이력과 불변식

재고를 바꾼 모든 시점은 `stock_ledger` 에 **변화량과 변화 후 값**으로 남습니다. 세 화면 모두
이 이력을 보여 주므로, 숫자가 이상하면 어느 처리에서 어긋났는지 되짚을 수 있습니다.

`stock.booked_quantity` 는 항상 **살아 있는 예약 행 수량의 합과 같아야 합니다.** 둘이 어긋나면
어느 쪽이 맞는지 알 수 없게 되므로, `ConcurrencyTest` 가 동시 예약 뒤 이 등식을 직접 확인합니다.

기준시각에 이미 잡혀 있던 예약(엑셀 `04_재고현황` 의 `ORD-PRE-001~006`)도 예약 행으로 남겼습니다.
앱이 모르는 주문이라 `order_id` 는 비우고 보유자만 `external_reference` 에 적었습니다. 합계로만
두면 "예약수량 2개를 누가 잡고 있는지" 를 화면에서 답할 수 없어서입니다. 가용재고 계산은 그대로
`booked_quantity` 를 쓰고, 이 행들은 그 숫자의 내역일 뿐입니다.

- 같은 주문 동시 예약 시 예약수량이 한 번만
늘어나는지, 가용재고를 넘기지 않는지,

- 동시에 피킹해도 같은 개체가 두 주문에 배정되지 않는지.

## 못 한 것과 남은 위험

1. **판정이 조회마다 전체 주문을 훑습니다.** 한 주문만 보더라도 전역 배분 결과 안에서의 값이어야
   의미가 있어 전체를 계산한 뒤 꺼냅니다. 목록 응답에 판정을 함께 실어 화면의 N+1 은 없앴지만,
   판정 자체는 매번 전 재고·전 주문을 읽습니다. 지금 데이터(주문 29건)에서는 문제가 없고
   수천 건까지는 버티겠지만, 그 위로는 증분 계산이나 캐시가 필요합니다.
2. **출고 취소와 예약 해제가 없습니다.** 시리얼 개체의 배정 해제만 있습니다. 과제 범위 밖이라
   넣지 않았는데 실제로는 필요합니다. 되돌리는 처리도 `stock_ledger` 에 반대 방향 이력으로
   남겨야 합니다.
3. **입고 예정일 지연 알림이 없습니다.** 사용 가능 예정일이 지났는데 입고되지 않은 문서를
   담당자가 직접 찾아야 합니다. 기준시각이 고정이라 지금 데이터로는 재현되지 않지만
   운영에서는 가장 먼저 필요한 알림일 것 같습니다.
4. **배송일 조정 요청을 앱 안에서 처리하지 못합니다.** 발주해도 납기를 못 맞추는 주문은 화면이
   "영업·CS에 배송일 조정을 요청하세요" 까지만 안내하고, 실제 전달과 회신은 앱 밖에서
   관리해야 합니다. 요청 상태를 주문에 붙여 두면 두 번 요청하거나 잊는 일을 막을 수 있습니다.
5. **기준시각 이전 예약의 원 주문 내용은 알 수 없습니다.** 엑셀에 `ORD-PRE-001~006` 이라는
   번호만 있습니다. 누가 얼마를 잡고 있는지는 화면에서 보이지만 그 주문 상세로 들어갈 수는 없습니다.
6. **인증과 담당자 개념이 없습니다.** 누가 예약하고 누가 검사 결과를 기록했는지 남지 않습니다.
   `stock_ledger` 에 처리자를 붙이는 게 맞습니다.
7. **화면 테스트가 계산 유틸 5개뿐입니다.** 업무 규칙은 서버에 있고 화면은 서버 값을 그리기만
   해서 서버 테스트를 우선했는데, 렌더링까지 덮으려면 E2E 가 필요합니다.
