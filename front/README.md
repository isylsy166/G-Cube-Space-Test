# Flowstock — 주문·재고·발주 통합 콘솔 (프론트엔드)

`back/` 의 Spring Boot API 를 쓰는 Next.js 프론트엔드입니다.
과제 요구사항(`.claude/01.REQUEST.md`) 4장의 화면 3개를 만들었습니다.

## 실행

```bash
npm install
npm run dev        # http://localhost:3000
```

백엔드(기본 `http://localhost:8080`)가 함께 떠 있어야 합니다. 주소가 다르면 `API_ORIGIN` 으로 바꿉니다.

```bash
API_ORIGIN=http://localhost:9090 npm run dev
```

브라우저는 언제나 같은 오리진의 `/api/*` 로만 호출하고, `next.config.ts` 의 rewrite 가
백엔드로 넘깁니다. 그래서 백엔드에 CORS 설정이 필요 없습니다.

## 화면

| 경로 | 요구사항 | 내용 |
| --- | --- | --- |
| `/orders` | 4-2 | 배송일별 주문 준비 현황. 예약 → 피킹 → 출고, 부족분 발주 진입점 |
| `/items` | 4-1 | 품목별 재고·개체·대기 주문·변동 이력 |
| `/schedules` | 4-3 | 구매발주·생산의뢰 문서, 확정·검사·입고 처리 |

---

## 화면을 이렇게 짠 이유

### 담당자의 축은 '배송일'이라고 봤습니다

주문 목록을 평평한 표가 아니라 **배송일로 묶고**, 각 주문에 `D-1`, `내일` 처럼 남은 일수를
세워 두었습니다. 배송일이 빠른 주문이 재고를 먼저 가져가는 규칙(3-3)이 화면 순서에 그대로
드러나야 담당자가 순서를 따로 머릿속에서 재구성하지 않습니다.

남은 일수는 실제 오늘이 아니라 **업무 기준시각 2026-07-21 09:00** 기준입니다.
백엔드가 고정 시계를 쓰므로 화면도 같은 값(`src/lib/basetime.ts`)을 씁니다.

### "이 범위에서 준비할 품목" 합계

요구사항 1장 첫 질문이 *"배송일별로 실제 준비해야 할 품목과 수량은 얼마인가"* 입니다.
주문 하나씩 열어 더하게 두지 않으려고, 지금 걸러 본 범위의 준비 수요를 **품목 단위로 합산**하는
표를 접었다 펼 수 있게 두었습니다. (`준비할 품목 보기`)

세트를 구성품으로 전개하고 서비스·취소 품목을 뺀 뒤의 수량이며, 부족한 품목이 위로 옵니다.
`필요 = 현재고 + 입고예정 + 부족` 으로 분해해 무엇을 얼마나 발주해야 하는지 바로 보입니다.

### 막힌 주문이 먼저 보이게

`재고 부족`은 주황, `확인 필요`는 회색으로 **줄 배경을 물들였습니다.** 배지만으로는 긴 목록에서
묻힙니다. 준비가 막힌 주문이 눈에 띄어야 한다는 4-2 의 요구를 색으로 풀었습니다.

### 필터는 셋 다, 그리고 건수를 먼저

4-2 가 요구한 **배송일·창고·준비상태** 세 축을 모두 칩으로 두었습니다. 각 칩에는 *그 축을 뺀
나머지 조건 기준* 건수를 붙여, 누르기 전에 몇 건이 남는지 알 수 있게 했습니다.
사용 중지된 창고는 칩에서부터 주황으로 구분합니다.

### 발주가 들어오면 어느 주문이 풀리는가

발주 문서 상세에 **`이 문서가 들어오면 풀리는 주문`** 과 **`이 문서를 만들게 한 주문`** 을
따로 두었습니다. 앞은 준비 판정의 `waitingScheduleCodes` 를 거꾸로 훑어 찾고, 뒤는 서버가
알려주는 생성 출처(`sourceOrderNumber`)입니다. 주문 → 발주 방향은 주문 상세의
`기다리는 입고 문서`로 이어집니다. (4-4)

### 상태는 코드로 판단하고, 글자는 서버 것을 씁니다

서버가 enum 을 `status`(코드)와 `statusLabel`(한글) 두 벌로 내려줍니다. 분기는 코드로 하고
화면에는 라벨을 그대로 씁니다. 업무 문구가 바뀌어도 로직이 흔들리지 않습니다.

명령이 실패했을 때도 **서버가 준 한글 사유를 그대로** 띄웁니다
(예: *"'재고 부족' 상태라 예약할 수 없습니다"*). 업무 규칙은 서버가 가장 정확히 압니다.

### 한 번의 처리가 세 화면에 함께 반영되도록

입고 하나로 다른 주문의 준비 상태가 바뀝니다(3-5). 그래서 명령이 성공하면 **열려 있는 데이터를
전부 다시 읽습니다**(`useRefreshAll`). 화면 일부만 갱신하면 숫자가 어긋나 보입니다.

예약·발주·입고 같은 명령에는 **`Idempotency-Key` 헤더**를 붙입니다. 네트워크 재시도로 같은
요청이 두 번 가도 서버가 한 번만 반영합니다(3-4, 3-5). 실행 중에는 버튼이 잠겨 이중 클릭도 막습니다.

### 상태는 URL 에 둡니다

선택·검색·필터가 모두 쿼리스트링에 남습니다.
(`/orders?due=2026-07-22&wh=WH-HQ&readiness=SHORTAGE&no=ORD...`)
새로고침해도 보던 화면이 유지되고, 그대로 공유할 수 있습니다.

## 구조

```
src/
  app/
    orders/     목록(배송일 그룹) · 상세 패널 · 준비 품목 합계(DemandRollup)
    items/      목록 · 상세 패널
    schedules/  목록 · 상세 패널 · 풀리는 주문 역참조(UnblockedOrders)
  components/
    AppShell    사이드바(네비·준비 현황 KPI) + 헤더·검색
    FilterBar   건수가 붙는 칩 필터 한 줄
    ui          배지·버튼·표·진행바·요약배너 등 공용 요소
    Toast       명령 결과 알림
    OrderRail   주문 진행 단계(접수→예약→피킹→출고)
  lib/
    types       백엔드 DTO 와 1:1 타입
    api         API 클라이언트. 명령에 Idempotency-Key 를 붙인다.
    hooks       SWR 조회 훅 + 명령 실행(useCommand)
    tone        상태별 색과 안내 문구
    basetime    업무 기준시각과 D-day 계산
    format      날짜·증감 표기
```

### 알아 둘 점

- **주문 진행 단계는 서버에 필드가 없어 되짚어 계산합니다.** 예약 내역·배정 개체·주문 상태를
  보고 판단하되, 뒤 단계가 끝났으면 앞 단계도 끝난 것으로 봅니다(비시리얼 주문은 피킹 흔적이
  남지 않기 때문). 실제 가능 여부는 서버가 명령 시점에 다시 검사합니다.
- **피킹 완료 판단은 개수 합계로만 합니다.** 개체 응답(`ItemUnitResponse`)에 품목코드가 없어
  품목별로 맞춰볼 수 없습니다. 품목별 부족은 서버가 출고 시점에 사유와 함께 막습니다.
- **준비 판정은 전체 주문을 함께 봐야 뜻이 통해** 목록을 한 번에 받아 화면에서 거릅니다.
  앞 주문이 재고를 먼저 가져가므로 서버 필터로 일부만 받으면 건수가 왜곡됩니다.
- **준비 품목 합계와 역참조는 필요할 때만 주문 상세를 받습니다.** 역참조는 대기·부족 주문으로
  후보를 좁히는데, 실제 데이터로 이 축소가 아무 주문도 놓치지 않음을 확인했습니다.

## 검증한 것 / 못 한 것

- 타입 검사, lint, 프로덕션 빌드 통과.
- 실서버 데이터로 **모든 enum 값이 색·문구 매핑에 존재**하는지 확인했습니다(누락 시 런타임
  오류가 되므로). 준비 상태 6종 전부 포함해 빠짐이 없습니다.
- 준비 수요 분해가 `필요 = 현재고 + 입고예정 + 부족` 으로 전 주문에서 맞는지 확인했습니다.
- **브라우저 화면은 직접 보지 못했습니다.** 서버 렌더 마크업과 데이터 계약 수준까지만 확인한
  상태라, 실제 렌더·상호작용은 한 번 눈으로 봐 주세요.

## 확인된 백엔드 이슈

`GET /api/items/{code}` 가 **품목 14건 모두에서 500** 을 돌려줍니다.
(목록 `GET /api/items`, 주문 상세, 발주 상세는 모두 정상)

이 때문에 제품 페이지의 **상세 패널이 "품목을 불러오지 못했습니다."로 표시됩니다.** 목록은
정상 동작합니다. 상세 패널은 DTO 계약대로 구현해 두었으므로 백엔드가 고쳐지면 그대로 동작합니다.

`ItemQueryService.findByCode` 는 `@Transactional(readOnly = true)` 이고 fetch join 도
걸려 있어 원인이 한눈에 드러나지 않았습니다. 서버 스택 트레이스 확인이 필요합니다.
